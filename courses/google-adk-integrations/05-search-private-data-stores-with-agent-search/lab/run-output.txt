answer According to the document **Postmortem: staging deploys stuck for 3 hours (2026-09-30)**:

### Why staging deploys got stuck
A deploy job was killed during a node drain while holding the PostgreSQL advisory lock for staging. Because the advisory lock was tied to the database session and the job's connection pooler kept that session open, the lock was never released. Consequently, subsequent staging deploys waited indefinitely at the "acquiring environment lock" step.

### What changed
* **Lock handling:** Deploy jobs now acquire the lock using `pg_try_advisory_xact_lock` inside a transaction, ensuring the lock automatically releases when the transaction ends.
* **Alerting:** An alert was added to trigger whenever an environment lock is held for longer than 20 minutes.
* **Documentation follow-up:** A task was assigned to the docs team to document how to manually release a stuck lock.

$ DOCS_TEAM=platform python agent.py "How do I rotate the release signing key, and when can I revoke the old one?"

answer Based on the document **"Runbook: rotate the release signing key"**, here is how to rotate the release signing key and when to revoke the old one:

### How to rotate the release signing key:
1. **Create the new key:** Run `docuctl keys create --purpose release-signing`. This stores the key under a new version while the old version remains valid.
2. **Promote the new key:** Run `docuctl keys promote <new-version>`. From this point forward, new releases will be signed with the new key.

### When to revoke the old key:
3. **Wait 7 days:** Allow 7 days so that every running release has either been redeployed or verified with the new key.
4. **Revoke the old key:** After the 7-day waiting period, revoke the old key by running:
   ```bash
   docuctl keys revoke <old-version>
   ```
   *(Note: Never delete or revoke the old version before waiting the 7 days; otherwise, releases signed with the old key will fail verification and cannot be rolled back to.)*
